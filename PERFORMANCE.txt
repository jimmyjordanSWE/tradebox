TradeBox native performance ledger
==================================

Purpose
-------
This is the append-only comparison record for compiler-option and core-code
performance experiments. Keep rejected experiments as evidence; do not replace
old results with a newer best run.

Measurement rules
-----------------
1. Use a clean MSVC x64 Release build and record the exact flags.
2. Close avoidable high-CPU applications and keep the same Windows power plan.
3. Preload benchmark corpora (the benchmark does this before timing).
4. Run at least two warm-ups, then use the median of nine IEX measurements.
5. Use at least one warm-up and the median of five SIP measurements.
6. Compare ingestion and durable throughput separately.
7. Treat changes smaller than 3% as noise until repeated on another day.
8. Run all correctness tests before accepting a compiler option or code change.

Profiling status
----------------
Windows Performance Recorder and Analyzer are installed. A WPR CPU-sampling
start failed with 0xc5585011 because this process lacks the system-profile
privilege. This is an elevation issue, not a WSL, Hyper-V, or VBS conflict.
No Windows security or virtualization feature was disabled.

The benchmark supports an optional final "profile" argument that reports time
spent in JSON/frame decoding, persistence queueing, in-memory projection, and
durable flush. These timings are diagnostic and must not replace the normal
un-instrumented throughput numbers.

Initial SIP phase profile before timestamp optimization:
  decode 3016.51 ms; persistence enqueue 186.38 ms;
  in-memory projection 986.39 ms; durable flush 230.17 ms.

SIP phase profile after timestamp optimization:
  decode 2205.93 ms; persistence enqueue 171.26 ms;
  in-memory projection 896.84 ms; durable flush 344.28 ms.
Decoder time fell 26.9%. It still accounts for about 67% of instrumented
ingestion time and remains the primary CPU optimization target. Flush time is
affected by asynchronous writer scheduling and should be compared through the
repeated uninstrumented durable-throughput result, not one phase-profile run.

Concurrency baseline
--------------------
The normal SIP benchmark uses a serialized decode/projection producer plus the
asynchronous database writer. One run reached a maximum of five process threads
but consumed about 1.41 equivalent CPU cores on average (6.44 process CPU
seconds over 4.56 wall seconds). The hot decoder and MarketDataStore projection
remain serialized.

Independent-process scaling probe, 500,000 SIP events per process:
  processes  total events  wall seconds  aggregate events/s  scaling
          1       500000          4.420              113114    1.00x
          2      1000000          5.396              185316    1.64x
          4      2000000          7.237              276376    2.44x

Interpretation: independent time-series work scales, but four-way efficiency is
already only about 61%. Do not create a thread per symbol or timeframe. The
first production experiment should use two bounded decoder workers:

1. The socket reader assigns a monotonically increasing frame sequence.
2. Two workers decode complete frames independently.
3. One ordered commit stage applies completed frames by sequence.
4. The existing database writer remains asynchronous.
5. Queue overflow is surfaced as a gap/safety condition; events are not dropped.

This preserves global broker order while parallelizing the current dominant
CPU phase. Keep MarketDataStore mutation serialized initially. Consider
instrument sharding only if profiling later shows projection, rather than
decoding, has become dominant.

Do not pin workers initially. Let the Windows scheduler place them; affinity can
reduce scheduler flexibility and worsen behavior across power states or
heterogeneous cores. Test affinity only as a recorded benchmark experiment.
