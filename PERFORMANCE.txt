TradeBox native performance ledger
==================================

Purpose
-------
This is the append-only comparison record for compiler-option and core-code
performance experiments. Keep rejected experiments as evidence; do not replace
old results with a newer best run.

Measurement rules
-----------------
1. Use a clean MSVC x64 Release build and record the exact flags.
2. Close avoidable high-CPU applications and keep the same Windows power plan.
3. Preload benchmark corpora (the benchmark does this before timing).
4. Run at least two warm-ups, then use the median of nine IEX measurements.
5. Use at least one warm-up and the median of five SIP measurements.
6. Compare ingestion and durable throughput separately.
7. Treat changes smaller than 3% as noise until repeated on another day.
8. Run all correctness tests before accepting a compiler option or code change.

Optimization-cycle build policy
-------------------------------
Use one optimized, symbol-capable build for all code-change comparisons:
baseline Release optimization plus /Zi /Zo and /DEBUG:FULL. Debug symbols do
not add application tracing or disable optimization; they let WPR resolve the
optimized code. Run ordinary throughput suites without an active WPR session,
and make targeted WPR captures from the same executable when call stacks are
needed. Continuously recording WPR would add profiler overhead and would make
the throughput number less representative, even if comparisons remained
nominally apples-to-apples.

At the eventual release pass, repeat the complete matrix with the shipping
symbol/debug-link policy and re-evaluate all compiler flags. Do not compare
numbers from that final build directly with the optimization-cycle baseline;
establish a separate release baseline.

2026-07-30 RapidJSON market-decoder experiment - in progress
Dependency: Tencent RapidJSON pinned to commit
24b5e7a8b27f42fa16b96fc70aade9106cf7102f.
Design: the decoder exposes four selectable modes for an apples-to-apples
comparison: direct+nlohmann fallback, direct+RapidJSON fallback,
nlohmann-only SAX, and RapidJSON-only SAX. Production retains the committed
direct+nlohmann default while the experiment is uncommitted.

SIP, 5 interleaved measured runs per backend:
  direct+nlohmann median ingestion/durable:
    299392 / 223401 events/s
  direct+RapidJSON median ingestion/durable:
    290734 / 216629 events/s
  nlohmann-only SAX median ingestion/durable:
    261522 / 217357 events/s
  RapidJSON-only SAX median ingestion/durable:
    294219 / 239942 events/s

Five interleaved phase-profile runs:
  nlohmann-only SAX median decode: 1035.32 ms
  RapidJSON-only SAX median decode: 859.04 ms
  RapidJSON parser-time change: -17.0%

Interpretation:
- RapidJSON SAX is materially faster than nlohmann SAX for the same canonical
  event builder.
- The direct parser remains faster than either library parser.
- Ordinary corpus frames never enter either fallback, so the two direct modes
  are functionally the same hot path; their end-to-end difference is system
  and asynchronous SQLite variance.
- Replacing only the fallback improves uncommon escaped/Unicode frames but
  cannot materially change normal stream throughput. Final acceptance should
  therefore prioritize semantic parity, dependency cost, and maintainability.

Concurrency baseline
--------------------
The normal SIP benchmark uses a serialized decode/projection producer plus the
asynchronous database writer. One run reached a maximum of five process threads
but consumed about 1.41 equivalent CPU cores on average (6.44 process CPU
seconds over 4.56 wall seconds). The hot decoder and MarketDataStore projection
remain serialized.

Independent-process scaling probe, 500,000 SIP events per process:
  processes  total events  wall seconds  aggregate events/s  scaling
          1       500000          4.420              113114    1.00x
          2      1000000          5.396              185316    1.64x
          4      2000000          7.237              276376    2.44x

Interpretation: independent time-series work scales, but four-way efficiency is
already only about 61%. Do not create a thread per symbol or timeframe. The
first production experiment should use two bounded decoder workers:

1. The socket reader assigns a monotonically increasing frame sequence.
2. Two workers decode complete frames independently.
3. One ordered commit stage applies completed frames by sequence.
4. The existing database writer remains asynchronous.
5. Queue overflow is surfaced as a gap/safety condition; events are not dropped.

This preserves global broker order while parallelizing the current dominant
CPU phase. Keep MarketDataStore mutation serialized initially. Consider
instrument sharding only if profiling later shows projection, rather than
decoding, has become dominant.

Do not pin workers initially. Let the Windows scheduler place them; affinity can
reduce scheduler flexibility and worsen behavior across power states or
heterogeneous cores. Test affinity only as a recorded benchmark experiment.

2026-07-30 narrow SQLite tick-index experiment (accepted)
---------------------------------------------------------
Build and workload: Release, tracing enabled, direct decoder with RapidJSON
fallback, 500,000-event SIP corpus, 1 warm-up plus 5 measured runs.

Previous same-code RapidJSON experiment median:
  ingestion: 290734 events/s
  durable:   216629 events/s

Narrow-index schema:
  ingestion min/median/mean/max/stddev:
    289616 / 292519 / 296653 / 311237 / 7809 events/s
  durable min/median/mean/max/stddev:
    245886 / 256554 / 253795 / 259182 / 5618 events/s

Median change:
  ingestion: +0.6%
  durable:  +18.4%

Accepted changes:
- Tick row ids use INTEGER PRIMARY KEY without AUTOINCREMENT.
- Deduplication indexes contain only rows with a non-null broker source id and
  omit the redundant kind column.
- Series indexes order equality keys before the time range:
  (instrument_id, feed, event_time_ns).
- Rare cancel/correction rows have small partial indexes so reconstruction can
  find out-of-range amendments without indexing kind for every quote/trade.
- Coverage and provider-bar indexes identical to their primary keys were
  removed.

Safety and correctness:
- WAL and synchronous=FULL remain enabled.
- Broker-id deduplication, exact decimals, correction/cancel reconstruction,
  restart persistence, and asynchronous failure surfacing are unchanged.
- All 162 tests pass after preserving the legacy symbol-only migration path.

Interpretation:
- SQLite itself was not the immediate limitation; the prior schema made every
  tick maintain wide or redundant B-trees.
- The next storage experiment should compact the wide nullable typed-tick row
  and its text keys. Do not weaken durability or checkpoint safety.
- A different engine is justified only if a compact SQLite layout still misses
  the required rate or exhibits unacceptable checkpoint tail latency.
